# Информационное табло на гибком модуле P2 — проект решения

Статус: v3. Цель — вывод данных из админки на LED-модуль.

> **v3 переписывает v1–v2.** Первые версии строились на «одной панели 64×32» и
> вели к прямому подключению ESP32. Фотография реального модуля показала другое
> железо, и выбор драйвера пришлось изменить. История в git.

## 0. Железо

| | |
|---|---|
| Модуль | `RX2.0-1515-160X80-40S-V1.0`, он же `P2-I40S-SMD1515-160x80` |
| Разрешение | **160 × 80 пикселей** (12 800 точек) |
| Физический размер | 320 × 160 мм, шаг 2 мм, светодиоды SMD1515 |
| Развёртка | **1/40** |
| Питание | 4-контактный разъём VCC/GND, максимум ~21 Вт (≈4,2 А при 5 В) |
| Особенность | Гибкий, радиус изгиба ограничен (Ø509 мм по шелкографии) |
| Есть в наличии | Orange Pi 3 LTS, ESP32, БП пока нет |

## 1. Почему не ESP32

Прямое подключение к микроконтроллеру для этого модуля закрыто, и дело не в
объёме данных.

**Развёртка 1/40 не ложится на HUB75.** При 80 строках и двух группах данных
(R1G1B1 / R2G2B2) нужно 40 шагов адресации, то есть 6 адресных линий.
Стандартный 16-контактный HUB75 несёт пять — A, B, C, D, E, максимум 1/32.
Значит модуль использует либо сдвиговый регистр выбора строки вместо двоичного
адреса, либо перепрофилирует линии. И то, и другое вне того, что умеет
`ESP32-HUB75-MatrixPanel-DMA` (там 1/2…1/32 с двоичной адресацией).

Такие модули рассчитаны на **приёмную карту** со скормленным ей файлом
конфигурации развёртки. Попытка завести их с ESP32 — это реверс-инжиниринг
схемы адресации с реальным шансом не получиться.

Вторым эшелоном: 12 800 пикселей это в 6 раз больше того, что уверенно тянет
ESP32-WROOM. Даже если бы развёртка совпала, упёрлись бы в RAM и мерцание.

## 2. Архитектура

```
Админка (backend)
  │  GET /api/display/{screen_id}  → display list (JSON)
  │  WiFi
  ▼
Orange Pi 3 LTS
  │  опрос API → рендер кадра 160×80 (Pillow, настоящие TTF)
  │  сырые L2-кадры Ethernet, протокол Colorlight
  ▼  (отдельный порт, без IP)
Colorlight 5A-75B  →  HUB75  →  модуль 160×80
```

Orange Pi наконец при деле, и роль у него правильная: он рендерер, а не
драйвер панели. Пиксели гоняет FPGA на приёмной карте.

**Два интерфейса Orange Pi заняты разным:** Ethernet отдан модулю целиком
(сырые кадры канального уровня, без IP-стека), в интернет и к админке Pi ходит
по WiFi. У Orange Pi 3 LTS есть и то, и другое.

Полоса: 160 × 80 × 3 байта = 38,4 КБ на кадр, при 30 к/с это 9 Мбит/с. Для
гигабитного порта — ничто.

## 3. Что уцелело от прежнего плана

Ошибочной оказалась ровно одна часть — выбор драйвера панели. Живут без
изменений:

- **формат display list** — примитивы отрисовки те же;
- **контракт API** и мок админки (`mock-server/server.py`);
- **`mock-server/render.py`** — из превью он становится боевым рендерером;
- **шрифты**: мелкий `f5` остаётся (нарисованный попиксельно, он всё ещё лучше
  TTF на 8 px), крупные кегли на Linux можно рисовать прямо из TTF любого
  размера, генератор больше не обязателен.

Прошивка ESP32 в `firmware/` **не удалена, а припаркована** — пригодится, если
позже добавится обычная панель HUB75 со стандартной развёрткой.

Не нужны: буфер уровней 74AHCT245 и вся возня с согласованием 3,3 → 5 В.
Приёмная карта выдаёт HUB75 сама.

## 4. Холст стал другим

160 × 80 против 64 × 32 — это в 6 раз больше площади. Прежний вывод «это
бегущая строка, а не дашборд» **больше не действует**: карусель из одной мысли
на экран не нужна, всё помещается сразу.

| шрифт | кириллицы в строке 160 px | строк на 80 px |
|---|---|---|
| `f5`  | 26 | 10 |
| `r12` | 12 | 5 |
| `b13` | 10 | 4 |
| `b16` | 8  | 4 |

Пример компоновки — `mock-server/sample-160x80.json`: счётчик мест, часы, три
комнаты со статусами, шкала загрузки и бегущая строка на одном экране.

Дистанция обзора для P2 — от ~2 м. Это не уличное табло на 10 метров, а экран
для помещения.

## 5. Контракт API

Без изменений относительно v2, добавлены только поля холста `w` и `h`.

```json
{
  "v": 1,
  "w": 160,
  "h": 80,
  "poll_interval": 20,
  "brightness": 55,
  "pages": [
    {
      "dwell": 12,
      "layers": [
        {"t":"text","x":2,"y":0,"f":"b16","c":"#00FF88","s":"7"},
        {"t":"clock","x":0,"y":0,"w":158,"a":"r","f":"b16","c":"#FFFFFF"},
        {"t":"bar","x":2,"y":64,"w":156,"h":4,"p":0.71,"c":"#FF9900","bg":"#182018"}
      ]
    }
  ]
}
```

Примитивы (`t`) и их поля:

| `t` | поля | назначение |
|---|---|---|
| `fill`   | `c` | залить весь кадр |
| `rect`   | `x y w h c fill` | рамка или прямоугольник |
| `line`   | `x y x2 y2 c` | линия |
| `text`   | `x y f c s` + `w a` | строка; `a` = `l`/`c`/`r` внутри `[x, x+w)` |
| `clock`  | `x y f c` + `w a` | локальное время ЧЧ:ММ |
| `scroll` | `x y w f c s sp` | бегущая строка, `sp` — px/с; не бежит, если влезает |
| `bar`    | `x y w h p c` + `bg` | шкала, `p` = 0..1 |

Общее: `x`/`y` — левый верхний угол (не базовая линия), `c` — `#RRGGBB`,
`f` — идентификатор шрифта. Неизвестный примитив пропускается молча.

`POST /api/display/{screen_id}/heartbeat` раз в минуту:
`{fw, uptime, rssi, free_heap, last_etag}`. В админке — список экранов с
отметкой «онлайн / молчит N минут». Без этого эксплуатация вслепую.

## 6. Что докупить

| Позиция | Зачем |
|---|---|
| **Colorlight 5A-75B** | Приёмная карта. Драйвит до 1024×256, наш модуль занимает малую часть |
| **БП 5 В, 6–8 А** | Модуль до 4,2 А плюс карта. На 5 А будет впритык |
| **Патч-корд Cat5e** | Orange Pi ↔ приёмная карта |
| **ПК с Windows** | Разово, для LEDVISION. Годится виртуалка |
| Отправляющая карта | **Только если** LEDVISION не сможет настроить приёмную напрямую — см. §7 |

Шлейф HUB75 и кабель питания обычно идут с модулем. Буфер уровней и всё, что
было в списке под ESP32, не нужно.

## 7. Главный риск: конфигурация приёмной карты

**Это gate. Пока он не пройден, остальная работа бессмысленна.**

Приёмная карта не знает, как устроена развёртка 1/40 конкретно этого модуля.
Ей нужен файл конфигурации, который загружается программой **LEDVISION**.
Варианты по убыванию удобства:

1. **Запросить `.rcfgx` у продавца модуля.** Самый быстрый путь, часто просто
   присылают. Спросить в первую очередь.
2. **«Умная настройка» (智能设置) в LEDVISION** — мастер задаёт вопросы вида
   «какие светодиоды загорелись» и выводит схему развёртки сам. Работает и для
   нестандартных модулей.
3. Если LEDVISION откажется работать без отправляющей карты — купить дешёвую
   (Colorlight S2 или аналог) разово, только ради конфигурации.

Пункт 3 — открытый вопрос: в сети есть сообщения, что 5A-75B настраивается
напрямую с сетевой карты ПК, и есть обратные. Проверять на живом железе,
закладывать бюджет на отправляющую карту как на страховку.

## 8. Второй риск: отправка кадров

Протокол Colorlight закрытый, но разобран и реализован в открытом коде:

- [q3k/chubby75](https://github.com/q3k/chubby75) — реверс-инжиниринг и документация плат
- [FalconChristmas/fpp](https://github.com/FalconChristmas/fpp/blob/master/src/channeloutput/ColorLight-5a-75.cpp) — зрелая рабочая реализация отправителя
- [kostaman/LED_Matrix-1](https://github.com/kostaman/LED_Matrix-1) — сетевой отправитель под Linux именно для 5A-75B/5A-75E
- [Разбор протокола у Harald Kubota](https://hkubota.wordpress.com/2022/01/31/winter-project-colorlight-5a-75b-protocol/)

**Реализовывать протокол с нуля по описанию в блоге не нужно.** Берём готовое,
адаптируем. Самостоятельная реализация — верный способ потерять неделю на
отладку кадров, которые уже кто-то отладил.

Техническая деталь: сырые кадры канального уровня требуют root или
`CAP_NET_RAW` на процессе.

## 9. План работ

| Этап | Содержание | Статус |
|---|---|---|
| 0. Закупка | Приёмная карта, БП, патч-корд | не начат |
| 1. **Gate: карта видит модуль** | LEDVISION, конфигурация развёртки, тестовая картинка | **блокирует всё** |
| 2. Отправка кадров | Raw socket на Orange Pi, заливка экрана цветом из Python | не начат |
| 3. Рендерер | `render.py` → кадр 160×80, TTF, вывод в отправитель | частично готов |
| 4. Сервис на Pi | Опрос API с ETag, кэш, systemd, ночная яркость, heartbeat | не начат |
| 5. Backend | Эндпоинт в админке | не начат |
| 6. Монтаж | Крепление гибкого модуля, питание, прогон 72 ч | не начат |

Этапы 1 и 2 — единственные с настоящей неопределённостью. Оценивать сроки до
прохождения этапа 1 честно нельзя: если карта не настроится, меняется план, а
не график.

Этапы 3 и 5 можно делать параллельно уже сейчас, против мока и превью.

## 10. Что лежит в репозитории

```
mock-server/     мок админки, эталонный рендерер, превью раскладки
  render.py            рендерер display list → кадр (станет боевым)
  server.py            мок админки: ETag, 304, токен, heartbeat
  sample-160x80.json   компоновка под этот модуль
tools/genfont.py генератор шрифтов

docs/led-hub75/
  DESIGN.md            этот файл
  WIRING.md            схема под ESP32 — устарела вместе с firmware/
```

## 11. Открытые вопросы

1. Один модуль или из них собирается лента/несколько сегментов? 5A-75B тянет
   намного больше одного модуля, и это стоит закладывать сразу.
2. Модуль монтируется плоско или изогнутым? От этого зависит крепление и то,
   не придётся ли корректировать геометрию картинки.
3. Какие метрики выводим? На 160×80 их помещается заметно больше, чем
   планировалось, — список стоит пересобрать.
