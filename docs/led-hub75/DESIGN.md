# Информационное табло на HUB75 — проект решения

Статус: v2. Цель — вывод данных из админки на LED-экран.

## 0. Зафиксированные вводные

- **Экран:** одна панель 64×32.
- **Бэкенд:** есть доступ на добавление собственного эндпоинта в админку.

Отсюда все решения ниже.

## 1. Итоговая архитектура

```
Админка (backend)
  │  GET /api/display/{screen_id}  → JSON: страницы + примитивы отрисовки
  │  ETag / If-None-Match
  ▼
ESP32-WROOM (WiFi, опрос раз в 15–30 с)
  │  парсит JSON → крутит карусель страниц → рисует примитивы
  ▼
HUB75 64×32
```

**Orange Pi 3 LTS в схеме не нужен.** Обоснование — §6.

## 2. Почему ESP32 драйвит панель напрямую

HUB75 — голая матрица со сдвиговыми регистрами: кто-то должен непрерывно, с
частотой 100–300 Гц, вручную гнать строки (BCM-развёртка). Варианты:

| Вариант | Вердикт для 64×32 |
|---|---|
| **ESP32 + `mrcodetastic/ESP32-HUB75-MatrixPanel-DMA`** | **Выбрано.** I2S DMA гонит панель без участия CPU |
| Orange Pi 3 LTS напрямую по GPIO | Нет. См. ниже |
| Colorlight 5A-75B + отправляющая карта | Избыточно на 2048 пикселей |

Про Orange Pi отдельно: каноничная `hzeller/rpi-rgb-led-matrix` написана под
BCM2835/2711 — пишет напрямую в регистры GPIO чипа Broadcom и завязана на его
тайминги. Orange Pi 3 LTS — это Allwinner H6, другая архитектура. Форки есть,
но дают мерцание и требуют изоляции ядра. В MVP этому места нет.

**Запас по ресурсам на 64×32:** 2048 пикселей — примерно 1/4 от того, что
классический ESP32 тянет уверенно. Полные 8 бит на канал, обновление >200 Гц,
свободной RAM и процессорного времени — с избытком.

## 3. Комплектующие

| Позиция | Что брать | Комментарий |
|---|---|---|
| Контроллер | ESP32-WROOM-32 devkit | Либо ESP32 Trinity — там буфер уровней уже на плате |
| Буфер уровней | 74AHCT245 | 3.3 В → 5 В. Не опционально, см. §5.1 |
| БП | 5 В, 4–5 А | Панель на белом поле берёт до 3.5 А |
| Панель | 64×32, шаг под дистанцию | P3 ≈ 192×96 мм, читается с 3+ м; P5 — с 5+ м |

Дефолтная распиновка библиотеки для ESP32 (менять без нужды не стоит):

```
R1=25  G1=26  B1=27      LAT=4
R2=14  G2=12  B2=13      OE =15
A =23  B =19  C =5  D=17 CLK=16
```
`E` не задействован — он нужен только для панелей 1/32 scan (64×64).

## 4. Вёрстка: 64×32 — это бегущая строка, а не дашборд

Самое важное следствие выбранного размера. Реальный бюджет площади:

| шрифт | высота | кириллицы в строке 64 px | строк на 32 px |
|---|---|---|---|
| `f5`  | 8 px  | 10 | 4 |
| `r12` | 15 px | 8  | 2 |
| `b13` | 17 px | 6  | 1 + мелкая строка |
| `b16` | 19 px | 5  | 1 |

Значения не прикидочные — измерены на собранных шрифтах
(`firmware/test/compare.py`). Для сравнения: «Свободно 7 из 24» это 87 px
даже мелким кеглем, то есть в панель не влезает в принципе.

Попытка уместить сюда «сводку по коворкингу» даст нечитаемую кашу. Правильная
модель — **карусель страниц**: одна мысль на экран, смена раз в несколько секунд.

Поэтому контракт API отдаёт не один кадр, а список страниц с временем показа.
Логика ротации — на ESP32 (это единственная логика, которую он себе позволяет),
состав и порядок страниц — на сервере.

## 5. Контракт API

`GET /api/display/{screen_id}`
Заголовки: `Authorization: Bearer <device_token>`, `If-None-Match: <last_etag>`.
Ответ `304 Not Modified` → ничего не перерисовываем, экономим и трафик, и RAM.

```json
{
  "v": 1,
  "poll_interval": 20,
  "brightness": 55,
  "pages": [
    {
      "dwell": 6,
      "layers": [
        {"t":"text","x":0,"y":0,"w":64,"a":"c","f":"f5","c":"#8899AA","s":"СВОБОДНО"},
        {"t":"text","x":2,"y":9,"f":"b16","c":"#00FF88","s":"7"},
        {"t":"text","x":14,"y":16,"f":"f5","c":"#FFFFFF","s":"из 24"},
        {"t":"bar","x":2,"y":27,"w":60,"h":3,"p":0.71,"c":"#FF9900","bg":"#182018"}
      ]
    },
    {
      "dwell": 8,
      "layers": [
        {"t":"clock","x":0,"y":1,"w":64,"a":"c","f":"b16","c":"#FFFFFF"},
        {"t":"scroll","x":0,"y":23,"w":64,"f":"f5","c":"#66CCFF","sp":16,
         "s":"Сегодня в 19:00 митап, регистрация на ресепшене"}
      ]
    }
  ]
}
```

Примитивы (`t`) и их поля:

| `t` | поля | назначение |
|---|---|---|
| `fill`   | `c` | залить весь кадр |
| `rect`   | `x y w h c fill` | рамка или прямоугольник |
| `line`   | `x y x2 y2 c` | линия |
| `text`   | `x y f c s` + `w a` | строка; `a` = `l`/`c`/`r` внутри `[x, x+w)` |
| `clock`  | `x y f c` + `w a` | локальное время ЧЧ:ММ, без запроса к серверу |
| `scroll` | `x y w f c s sp` | бегущая строка, `sp` — px/с; не бежит, если влезает |
| `bar`    | `x y w h p c` + `bg` | шкала, `p` = 0..1 |

Общее: `x`/`y` — левый верхний угол (не базовая линия), `c` — `#RRGGBB`,
`f` — идентификатор шрифта. Неизвестный примитив прошивка молча пропускает,
поэтому новые типы можно добавлять на сервере, не ломая старые табло.

**Телеметрия.** `POST /api/display/{screen_id}/heartbeat` раз в минуту:
`{fw, uptime, rssi, free_heap, last_etag}`. В админке — список экранов с
отметкой «онлайн / молчит N минут». Без этого эксплуатация вслепую: табло
может показывать вчерашние данные, и никто не узнает.

## 6. Что вынести на сервер, а что оставить в прошивке

Правило: **ESP32 максимально тупой.** В прошивке — только то, что физически
нельзя отдать наружу:

| В прошивке | На сервере |
|---|---|
| Рендер примитивов, шрифты | Какие данные показывать |
| Ротация страниц по `dwell` | Состав и порядок страниц, тексты, цвета |
| Анимация скролла | Пороговые значения, форматирование чисел |
| NTP, реконнект, кэш, OTA | Расписание яркости (отдаёт `brightness`) |

При таком разделении перепрошивка нужна только для нового *типа* примитива.
Всё остальное правится на бэкенде и приезжает в течение `poll_interval`.

**Orange Pi понадобится позже, если появится** одно из: сложная авторизация с
refresh-токенами (Pi возьмёт TLS и токены на себя, ESP32 будет ходить по plain
HTTP в локалку); потребность в настоящей типографике и графике (Pi рендерит
кадр в Pillow и отдаёт готовый RGB565 — 4 КБ на 64×32, на LAN это ничто);
много экранов и нужен единый кэш. Сейчас — не нужен.

## 7. Подводные камни

1. **Уровни 3.3 → 5 В.** Выходы ESP32 3.3 В, логика HUB75 5 В. Часто работает
   «на честном слове», но на длинном шлейфе лезут артефакты и случайные
   пиксели. Ставить `74AHCT245` (именно AHCT, не HC — у HC порог переключения
   выше 3.3 В) или взять готовую плату с буфером.
2. **Питание — причина №1 «случайных» перезагрузок.** Общая земля панели и
   ESP32 обязательна. Питать ESP32 от того же 5 В через VIN. Ограничение
   яркости до 60–70 % почти не влияет на восприятие, но кратно снижает ток.
3. **Кириллица.** Шрифты Adafruit GFX по умолчанию только ASCII. Нужно:
   сгенерировать шрифт через `fontconvert` с диапазоном 0x0400–0x04FF и
   добавить декодер UTF-8 → codepoint перед отрисовкой. Работы 1–2 часа, но
   это классическая ловушка «всё собрано, а на экране кракозябры».
4. **WiFi в точке монтажа.** Замерить RSSI *до* монтажа. Ethernet-варианты
   ESP32 (WT32-ETH01, ESP32-POE) конфликтуют по пинам с HUB75 — не закладываться.
5. **Обрыв сети.** Обязателен кэш последнего валидного JSON в NVS плюс
   визуальный индикатор устаревших данных (например, точка в углу после
   2×`poll_interval` без успешного ответа). Иначе табло молча врёт.

## 8. План разработки

| Этап | Содержание | Статус |
|---|---|---|
| 1. Bring-up железа | ESP32 + панель + БП + буфер, проверка распиновки и цветов | ждёт железа |
| 2. Контракт API | Схема display list, мок админки | **готово** |
| 3. Каркас прошивки | WiFi + NVS-конфиг, NTP, HTTP с ETag, ArduinoJson | **написано, не собрано** |
| 4. Рендерер | Примитивы, кириллический шрифт, скролл, карусель, двойная буферизация | **готово, проверено на хосте** |
| 5. Backend | Реальный эндпоинт в админке + heartbeat | не начат |
| 6. Надёжность | OTA, сторожевой таймер, кэш в NVS, экран ошибки | **написано, не собрано** |
| 7. Монтаж | Крепёж, питание, проверка WiFi на месте, прогон 72 ч | ждёт железа |

**Что уже можно делать без панели:** верстать страницы и смотреть их в превью
(`mock-server/render.py`), писать эндпоинт в админке против зафиксированного
контракта и сверять его с моком.

**Чего проверить нельзя, пока нет железа:** прошивка не собиралась компилятором
ESP32 — реестр PlatformIO недоступен из среды разработки, поэтому Arduino-часть
(`net.cpp`, `storage.cpp`, `main.cpp`) вычитана глазами, но не скомпилирована.
Слой отрисовки собран хостовым компилятором и покрыт тестом. Первая сборка на
машине с интернетом почти наверняка потребует поправить версии в `lib_deps`.

Порядок остального: бэкенд и прошивка едут параллельно против общего мока и
встречаются только на монтаже.

## 9. Что лежит в репозитории

```
firmware/      прошивка ESP32 (PlatformIO)
  src/gfx.*            растеризация: UTF-8, глифы, примитивы
  src/display_list.*   интерпретатор display list
  src/net.*            WiFi, HTTP с ETag, NTP, OTA, heartbeat
  src/storage.*        конфиг и кэш в NVS, настройка по Serial
  src/fonts.*          сгенерированный растр шрифтов
  test/compare.py      сверка отрисовки прошивки с эталонной
mock-server/   мок админки, эталонный рендерер, превью раскладки
tools/genfont.py генератор шрифтов
```

Ключевая деталь: прошивка и превью используют один и тот же растр шрифтов
(`tools/genfont.py` порождает и `fonts.cpp`, и `fonts.json`), а
`firmware/test/compare.py` сверяет обе реализации отрисовки пиксель в пиксель.
Иначе превью показывало бы одно, а панель — другое, и ловить это пришлось бы
уже на смонтированном табло.

## 10. Открытые вопросы

1. Какой шаг пикселя у панели и с какой дистанции на неё смотрят? От этого
   зависит выбор размера шрифта и предельная длина строк.
2. Какие конкретно метрики выводим и сколько их — это определяет число страниц
   карусели и суммарное время полного цикла.
3. Планируется ли второй экран? Если да, `screen_id` и разделение контента
   закладываем сразу — переделывать потом дороже.
