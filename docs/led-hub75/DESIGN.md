# Информационное табло на HUB75 — проект решения

Статус: черновик v1. Цель — вывод данных из админки на LED-экраны.

## 1. Ключевое решение: кто драйвит HUB75

HUB75 — это не "экран с драйвером", а голая матрица со сдвиговыми регистрами.
Кто-то должен непрерывно, с частотой 100–300 Гц, вручную обновлять строки
(BCM/PWM разверткой). Это и есть главный архитектурный выбор.

| Вариант | Кто рисует | Сложность | Вердикт |
|---|---|---|---|
| **ESP32 + ESP32-HUB75-MatrixPanel-DMA** | I2S/LCD DMA прямо в панель | Низкая | **Рекомендуется для MVP** |
| Orange Pi 3 LTS напрямую (GPIO) | CPU bit-banging | Высокая | **Не брать** |
| Colorlight 5A-75B + отправляющая карта | FPGA-приёмник, Ethernet | Средняя/высокая | Только если >64k пикселей |

### Почему не Orange Pi напрямую

Каноничная библиотека `hzeller/rpi-rgb-led-matrix` написана под BCM2835/2711
(Raspberry Pi): она пишет напрямую в регистры GPIO чипа Broadcom и использует
особенности его таймингов. Orange Pi 3 LTS — это Allwinner H6, другая
архитектура GPIO. Форки существуют, но нестабильны, дают мерцание и требуют
изоляции ядра. Тратить на это время в MVP нельзя.

**Роль Orange Pi в этом проекте — не драйвер панели, а опциональный локальный
шлюз/рендерер** (см. §5). В MVP он вообще не нужен.

### Почему ESP32

- WiFi «из коробки» → сам ходит в API админки, промежуточных звеньев ноль.
- Библиотека `mrcodetastic/ESP32-HUB75-MatrixPanel-DMA` — зрелая, DMA, панель
  обновляется без участия CPU, ядро свободно под сеть и логику.
- Загрузка ~1 сек, нет ОС, нет SD-карты (главный источник смертей у Pi-табло),
  нет «протухшей» файловой системы после отключения питания.
- Стоимость узла ~$5.

**Ограничение по разрешению (классический ESP32, WROOM):** уверенно —
до 128×64 при 8-битной глубине цвета. 256×64 работает при снижении глубины до
4–5 бит. Больше — брать **ESP32-S3 с PSRAM** (та же библиотека, LCD-периферия,
запас по RAM) или уходить на Colorlight.

## 2. Целевая архитектура MVP

```
Админка (backend)
  │  GET /api/display/{screen_id}   → компактный JSON "display list"
  │  ETag / If-None-Match, ttl, poll_interval
  ▼
ESP32 (WiFi, опрос раз в N сек)
  │  парсит JSON → интерпретирует как список примитивов отрисовки
  ▼
HUB75 панели (цепочка)
```

**Главный принцип: ESP32 максимально тупой.** Вся бизнес-логика, все правила
«что показывать» — на сервере. Прошивка — это интерпретатор списка примитивов.

Три уровня «тупости», выбираем средний:

- **A. JSON с полями** (`{"free": 7, "next_booking": "14:30"}`), вёрстка зашита
  в прошивку. Смена данных — без перепрошивки, смена вёрстки — с перепрошивкой.
  Слишком жёстко.
- **B. Display list (выбрано).** Сервер отдаёт список примитивов: текст, рамка,
  прогресс-бар, бегущая строка, иконка. Прошивка — рендерер. Вёрстка меняется
  на сервере, перепрошивка нужна только для новых типов примитивов.
- **C. Готовый фреймбуфер.** Сервер рендерит картинку (Pillow + настоящие TTF),
  шлёт RGB565 (128×64 = 16 КБ). Максимум красоты, любые шрифты и графика,
  но нужен Orange Pi и нет автономности при обрыве сети. **Путь апгрейда.**

## 3. Контракт API

`GET /api/display/{screen_id}` , заголовки: `Authorization: Bearer <device_token>`,
`If-None-Match: <last_etag>`. Ответ `304` — ничего не перерисовываем.

```json
{
  "v": 3,
  "ttl": 60,
  "poll_interval": 15,
  "brightness": 60,
  "layers": [
    {"t":"fill","c":"#000000"},
    {"t":"clock","x":96,"y":2,"f":"b12","c":"#FFFFFF","fmt":"HH:mm"},
    {"t":"text","x":2,"y":2,"f":"b12","c":"#00FF88","s":"Свободно: 7"},
    {"t":"text","x":2,"y":20,"f":"r8","c":"#FFFFFF","s":"Переговорка A — до 14:30"},
    {"t":"bar","x":2,"y":32,"w":124,"h":4,"p":0.72,"c":"#FF9900"},
    {"t":"scroll","x":0,"y":52,"w":128,"f":"r8","c":"#FFFFFF","sp":20,
     "s":"Сегодня в 19:00 — митап. Регистрация на ресепшене."}
  ]
}
```

Поля: `t` — тип примитива, `f` — идентификатор шрифта из зашитого набора,
`p` — заполнение бара 0..1, `sp` — скорость скролла (px/сек).

`POST /api/display/{screen_id}/heartbeat` — устройство раз в минуту шлёт
`{fw, uptime, rssi, free_heap, last_etag}`. В админке — список экранов с
индикатором «онлайн / молчит N минут». Без этого эксплуатация вслепую.

## 4. Что важно не забыть в железе

1. **Уровни 3.3 → 5 В.** Выходы ESP32 3.3 В, логика HUB75 5 В. Часто работает
   «на честном слове», но на длинном шлейфе начинаются артефакты. Ставить
   буфер `74AHCT245` или брать готовую плату (ESP32 Trinity / MatrixPortal S3).
2. **Питание.** Панель 64×32 — до ~3.5 А @5 В на белом поле, типично 1–2 А.
   БП 5 В с запасом ×1.5, толстые провода, **инжекция питания в каждую панель**
   отдельно, общая земля с ESP32. Ограничение яркости до 60–70 % экономит
   львиную долю тока и продлевает жизнь БП.
3. **Кириллица.** Шрифты Adafruit GFX по умолчанию только ASCII. Нужно:
   сгенерировать шрифт `fontconvert` с диапазоном 0x0400–0x04FF + добавить
   декодер UTF-8 → codepoint перед отрисовкой. Работы ~1–2 часа, но это
   классическая ловушка «всё готово, а текст в кракозябрах».
4. **Сеть.** WiFi в местах монтажа табло часто слабый. Проверить RSSI в точке
   установки *до* монтажа. Вариант с Ethernet на ESP32 (WT32-ETH01, ESP32-POE)
   конфликтует по пинам с HUB75 — закладываться на него не стоит.

## 5. Когда подключать Orange Pi 3 LTS

Не в MVP. Он оправдан, когда появится хотя бы одно из:

- API админки требует сложной авторизации / refresh-токенов / тяжёлого TLS —
  Orange Pi берёт это на себя, ESP32 ходит по plain HTTP в локалку.
- Нужна красивая типографика, графики, логотипы, анимация — переход на
  вариант C: Pi рендерит кадр в Pillow и отдаёт готовый фреймбуфер.
- Экранов много и хочется единую точку кэша/раскладки контента.

Тогда: `Админка → Orange Pi (Python: poll + transform + render) → MQTT/HTTP в
локалке → N × ESP32`.

## 6. План разработки

| Этап | Содержание | Оценка |
|---|---|---|
| 0. Требования | Состав панелей, дистанция обзора, точный перечень данных | 0.5 д |
| 1. Bring-up железа | ESP32 + 1 панель + БП, примеры библиотеки, цепочка из N | 1 д |
| 2. Контракт API | Зафиксировать схему display list, поднять мок (статический JSON) | 0.5 д |
| 3. Каркас прошивки | WiFi + NVS-конфиг, NTP, HTTP-клиент с ETag, ArduinoJson | 1–2 д |
| 4. Рендерер | Интерпретатор примитивов, кириллический шрифт, скролл, двойная буферизация | 2 д |
| 5. Backend | Реальный эндпоинт в админке, сборка display list из данных | 2 д (параллельно) |
| 6. Надёжность | OTA, watchdog, кэш последнего кадра в NVS, экран ошибки, ночное затемнение, heartbeat | 2 д |
| 7. Монтаж | Питание, крепёж, проверка WiFi на месте, прогон 72 ч | 1–2 д |

**MVP на столе — 3–5 рабочих дней. Продакшн — 2–3 недели.**

Порядок важен: этап 2 (контракт) делается до этапа 3, и бэкенд с прошивкой
после этого едут параллельно против мока.

## 7. Риски

- **Мерцание при большой цепочке.** Митигация: замерить реальную частоту
  обновления на этапе 1, до заказа остальных панелей. Если мало — ESP32-S3.
- **Кириллица** — см. §4.3, закладывать время явно.
- **Обрыв сети** — обязателен кэш последнего валидного кадра в NVS плюс
  визуальный индикатор «данные устарели», иначе табло молча врёт.
- **Питание** — самая частая причина «случайных» перезагрузок и артефактов.

## 8. Открытые вопросы

1. Сколько панелей, какой размер (64×32 / 64×64) и шаг (P2.5/P3/P4/P5)?
   Итоговое разрешение определяет ESP32 vs ESP32-S3 vs Colorlight.
2. Какие именно данные из админки выводим и с какой периодичностью обновления?
3. Есть ли доступ на добавление эндпоинта в бэкенд админки, или читаем
   существующий API как есть?
4. Один экран или сеть экранов с разным контентом?
