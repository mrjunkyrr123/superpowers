## Цель

Настольная/настенная панель на ESP32-S3 с сенсорным экраном: показывает данные
из админки коворкинга (брони, свободные места, статусы комнат) и имеет
сенсорные кнопки, которые шлют действия на сервер. Сервер отдаёт «display
list» — список примитивов отрисовки, устройство их рисует. Вёрстка и кнопки
меняются на сервере без перепрошивки.

## Железо — подтверждено на реальной плате

Плата **Guition ESP32-S3-4848S040**, 4″, 480×480, в корпусе 100×100 мм.
Пользователь получил её, она подключена к компьютеру.

| | |
|---|---|
| Порт | **COM10** (мост CH340) |
| Чип | ESP32-S3 (QFN56) rev v0.2 |
| PSRAM | 8 МБ встроенная, **octal** |
| Флеш | 16 МБ, **quad** |
| Экран | ST7701S, параллельный RGB |
| Сенсор | GT911 по I²C, SDA 19, SCL 45, адрес 0x5D или 0x14, INT/RST не разведены |
| Подсветка | GPIO 38 |
| Микрофона | нет |

Отсюда `board_build.arduino.memory_type = qio_opi`. С неправильным типом PSRAM
не найдётся, и кадровый буфер 480×480 (460 КБ) не создать.

## Выученное на железе

- **Порт только 460800.** На 921600 CH340 бьёт пакеты (`Corrupt data`).
- **Bounce-буферы обязательны** (`board.cpp`, `SCREEN_W * 10`). Без них запись
  в PSRAM отнимает поток у экрана (PCLK 12 МГц, кадр в PSRAM) — картинка
  мерцает и дрожит вбок. Подтверждено: с ними дрожь ушла.
- **Скорость:** полный кадр ~75 мс отрисовка + ~35 мс вывод. Полная перерисовка —
  только по событию (смена экрана, касание, данные). Бегущая строка, которая не
  влезает по ширине, перерисовывает только свою полосу (`drawBands`, ~28 мс →
  25 кадров/с). Анимацию на весь кадр не делать — вернётся дрожь.
- `PixelSink::hline()` — быстрые заливки и отрезки глифов; по умолчанию по
  точке, так что табло HUB75 рисует как раньше.
- **`compare.py` после правки `gfx.cpp` не прогнан** — на Windows нет хостового
  C++. По построению пиксели те же, но проверить: облачная сессия или поставить
  компилятор (спросить владельца, ~400 МБ).
- Сборка иногда падает вылетом gcc (`Error 3221225477`) на файлах Arduino_GFX —
  не наш код, `flash.ps1` повторяет сам.
- Серые дизайнера на плате выглядят нормально (розового оттенка владелец не заметил).

## Шаг B — живые данные (следующий)

### B1. Сервер: эндпоинт в `rec-room-api`

Код: `c:\My project\рекорум\rr_admin\rr_admin v3` (bun). Выкатка — скилл
`rr-deploy`, после неё `rr-verify`; тесты — `rr-tests`. На прод — только после
«да» владельца.

- Эндпоинт вида `GET /api/display/<screen>` (прошивка уже ходит на
  `<url>/api/display/<screenId>`, см. `firmware/src/net.cpp`) — отдаёт готовый
  display list в формате прошивки (как `mock-server/dashboard-480x480.json`), с
  `ETag`, `304`, `poll_interval`, `brightness`.
- Данные — те же, что у «Пульта» (`tickets/assets/2026-10-21-statistics/` в rr_md).
  Поля `bind` и пороги проблем — в README дизайнера.
- Генерация раскладки — на сервере. Не просто подстановка `bind`: число точек,
  до 4 карточек «Внимания», цвета статусов (ok/warn/crit), высоты столбиков
  недели, риска «по темпу» — всё считается из данных. Ориентир по геометрии —
  `layout.json` и `make.py` дизайнера.
- Правила показа: «Внимание» только при проблемах; при красной — первым и 30 с;
  без проблем — на «Сейчас» зелёная плашка «Всё в норме» (цвет `ok`, без бегущей строки).
- Полоски номера экрана внизу — рисовать по фактическому числу экранов (4 или 5).
- Приём нажатий кнопок: `POST` на `path` кнопки. Сейчас кнопок на дашборде нет;
  дизайнер предлагал «Понял» 448×56 на «Внимании» — скрывает проблему до завтра.

### B2. Токен устройства

Решение владельца: **не админский логин и не «только чтение»** — владелец
планирует кнопки управления админкой. Предложено (владелец ещё не подтвердил —
спросить): у каждой панели свой токен; разрешает читать свою раскладку и
вызывать только те действия, что сервер сам повесил на кнопки этой панели.
Токен — в Bitwarden (`$env:...`), на плату — через Serial в NVS, не в git.

### B3. Прошивка: сеть

- Подключить `firmware/src/net.cpp` и `storage.cpp` в `panel-4848` через
  `build_src_filter` (как `gfx.cpp`). Они общие с HUB75 и от HUB75 не зависят.
- Они берут `#include "secrets.h"` из **`firmware/src/secrets.h`** (кавычки ищут
  рядом с файлом). Файл в `.gitignore`; создать из `secrets.example.h`, пустые
  SSID/пароль, `TZ_INFO "MSK-3"`, свой `OTA_PASSWORD`.
- Wi-Fi: гостевая сеть `DNEPROOM`. Пароль владелец называл в чате; в git, код и
  этот файл не класть — записать в NVS платы через Serial: `set ssid DNEPROOM`,
  `set pass ...`, `set url ...`, `set token ...`, `save` (см. `storage.h`).
- **Кэш:** `CACHE_MAX = 3500` байт (NVS), а раскладка ~14 КБ — не сохранится, и
  без сети плата покажет пустоту. Нужен кэш в LittleFS (флеш 16 МБ) или NVS-blob.
  Запасной вариант — `layout_embedded.h`, но с примерными цифрами: тогда явно
  помечать «нет данных».
- **Под 480×480 переделать:** метку «данные устарели» (сейчас 1 пиксель в углу,
  `display_list.cpp`) и `renderStatus()` (шрифт `f5` 5 px — на 480 не читается).
  Это общий код с HUB75 — менять так, чтобы HUB75 не сломался (например, размеры
  от `ctx.w`).
- Часы: `localTimeStr()` из `net.cpp` вместо `"--:--"` в `makeCtx()`; перерисовка
  по смене минуты.
- Новые данные с сервера → `dirty = true`; не сбрасывать текущий экран, если
  число экранов не изменилось; `pressedId` — копия, документ может смениться
  под пальцем (так уже сделано).
- Кнопка → `POST` на `<url><path>` с токеном (`hitTest()` уже даёт `method`/`path`).
- Перед подключением к реальному API — проверить на мок-сервере на компе
  (`mock-server/server.py`). Плата и компьютер в одной сети. Брандмауэр Windows
  спросит разрешение для python — разрешает владелец, не Claude.

## Правила, которые выработались

- **Проверять компилятором и тестами, а не на глаз.** После правок в
  `firmware/src` гонять `python firmware/test/compare.py` (на Windows нет C++ — см. выше).
- **Не утверждать «работает», пока не видели на железе.** Говорить отдельно,
  что собрано, а что запущено.
- Действие кнопки — **путь**, не полный URL. Устройство подставляет базовый
  адрес из настроек и не может постучаться на чужой хост. Не ломать это.
- Коммиты — в эту ветку, понятные сообщения. Пушить после каждого шага.
